🔴 严重问题 (Critical)

C-1 网络层文件系统暴露：默认监听 0.0.0.0 + 可读整个 $HOME + 无认证 CriticalSecurity
cli/analyze.py:104 · backend/api/main.py:38-40

三个问题叠加构成可被网络直接利用的高危链路：

# cli/analyze.py:104 — 绑定所有网卡（用户提示却写的是 localhost）
kwargs={"app":"backend.api.main:app", "host":"0.0.0.0", "port":port, ...}

# main.py:38-40 — 默认允许分析整个 home 目录
_ALLOWED_BASE = Path(os.environ.get("ALLOWED_BASE_DIR", Path.home())).resolve()

所有接口无任何认证。任意局域网内的客户端均可提交分析请求，读取 $HOME 下全部 Python 文件内容（含 dotfiles、脚本中的凭据等），并通过分析结果 / HTML 报告回传。

修复：默认绑定 127.0.0.1；ALLOWED_BASE_DIR 默认收窄到被分析项目目录本身而非 home；为接口增加认证（如 token）。
C-2 重复检测标记串扰：同名 qualname 导致 is_duplicate 互相覆盖 CriticalBug / 正确性
backend/analyzer/core.py:160-166 
fn_lookup = {f"{fn.file}::{fn.qualname}": fn.is_duplicate for fn in all_functions}
for fi in file_infos:
    for fn_dict in fi["functions"]:
        key = f"{fi['relative_path']}::{fn_dict['qualname']}"
        fn_dict["is_duplicate"] = fn_lookup.get(key, False)

qualname 在同一文件内并不唯一：@property 与其 @x.setter 同为 C.v；@overload 桩函数与真实实现同名；条件重定义函数同名。字典推导只保留最后一个同名函数的值，并回写到所有同名 fn_dict 上。

结果：误标重复、污染喂给风险评分（risk.py:71 的 dup_ratio）和 Top 重复列表的逐文件记录。更糟的是 all_functions（喂给汇总计数）是正确的，导致汇总视图与逐文件视图自相矛盾。

修复：在 detect_duplicates 之后再构建 _fn_to_dict；或用包含 line_start 的唯一键 f"{file}::{qualname}::{line_start}"。
C-3 符号链接逃逸：遍历项目时跟随指向 $ALLOWED_BASE 之外的软链 CriticalSecurity
backend/api/main.py:43-54, 122-123（守卫仅校验顶层路径）

_assert_safe_path 只对提交的顶层路径做 relative_to(_ALLOWED_BASE) 校验。但 analyze_project 随后遍历目录树时会跟随项目内部的符号链接，遍历期间发现的文件路径未再校验。项目目录内任意一个指向 /etc/passwd 等位置的软链都会被读取并出现在报告中。

修复：对遍历过程中发现的每个文件路径（解析软链后）重新校验是否落在 _ALLOWED_BASE 内；或在 os.walk 中禁用 followlinks。
C-4 任务超时不会终止运行，且迟到完成会覆盖超时状态、耗尽线程池 CriticalConcurrency / Bug
backend/api/tasks.py:285-302 
future = _executor.submit(_run)
def _watchdog():
    try:
        future.result(timeout=ANALYSIS_TIMEOUT)
    except FutureTimeoutError:
        ... _update(task_id, status="failed", ... "exceeded ... limit")

超时仅标记任务失败，_run 线程仍在执行（ThreadPoolExecutor 无法取消运行中的线程）：① 继续占用 CPU/内存与一个 worker 槽位；② 卡死的任务永久占用 worker，默认 4 个卡死即阻塞所有后续提交；③ 当 _run 最终完成时调用 _update(status="completed")，覆盖掉之前的超时失败状态（对 _store 与 DB 行产生竞态）。

修复：用 ProcessPoolExecutor 以便超时时杀死进程，或让 analyze_project 轮询取消标志；并在覆盖前检查当前状态是否已是终态。

🟠 高危问题 (High)

H-1 SLOC 误算：多行字符串 / docstring 内以 # 开头的行被当作注释 HighBug / 正确性
backend/analyzer/metrics.py:25-31

count_lines 纯文本扫描，不识别字符串字面量。三引号字符串里一行 exitstr = "# not a comment" 或 docstring 内的 # 行会被误判为注释而从 SLOC 中扣除，使每个含多行字符串/docstring 的文件 SLOC 系统性偏低。

修复：用 tokenize.generate_tokens 识别真正的 COMMENT token 与跨行字符串；AST 在 core.py:115 已解析一次，可复用。
H-2 splitlines() 在异常行分隔符上高估 LOC High正确性 / 健壮性
backend/analyzer/metrics.py:21

str.splitlines() 会在整套 Unicode 行边界处切分（\x0b 垂直制表、\x0c 换页、\x85、 /  等），而 Python 词法分析器并不把这些当行终止符。已验证 count_lines('a\x0bb') 返回 loc=2。.py 中合法的换页符会膨胀 LOC 并使行计数与 AST 行号不一致。

修复：显式按 \n/\r\n 切分（source.split("\n") 后去尾随 \r），匹配 Python 自身的行模型。
H-3 限流器非线程安全且无限增长（内存耗尽向量） HighConcurrency / 内存泄漏
backend/api/main.py:84, 87-101

_rl_store 从不删除 IP 条目——每个不同客户端 IP 永久占用一个 dict 条目（无界增长）。攻击者经代理伪造/变化源 IP 即可耗尽内存。此外 request.client.host 是 socket 对端，置于反向代理之后会把所有客户端折叠到同一个桶。

修复：定期清理修剪后为空的 deque / 过期 IP；若限流可能脱离事件循环运行需加锁。
H-4 README 声称有 GitHub Actions CI，实际无 .github/ 目录 HighMissing / 文档失实
仓库根（无 .github/）· README.md:22, 344-346

已确认仓库无任何 workflow 文件。README 却描述 "Python 3.10/3.11/3.12 矩阵 + ≥70% 覆盖率门控" 以及对 main、feature/**、claude/** 的推送触发。项目被宣传为 CI 门控但零自动化。

修复：新增 .github/workflows/ci.yml 实现所述矩阵 + 覆盖率门控；否则从 README 删除 CI 声明。
H-5 缺少运行时 requirements.txt，安装命令手敲且依赖标注有误 HighMissing / Config
仓库根（仅有 requirements-dev.txt）· README.md:90

修复：新增 requirements.txt（fastapi、uvicorn、pydantic、networkx）并改用 pip install -r；从运行时安装行去掉 httpx。
H-6 前端无 Error Boundary，渲染异常导致整页白屏 High健壮性
frontend/src/（全局无 componentDidCatch/ErrorBoundary）

懒加载页面直接基于 result 渲染 ECharts。任何渲染期异常（畸形 payload、ECharts option 错误、chunk 加载失败）都会卸载整个应用、只在 console 留错，无任何降级 UI。

修复：用错误边界组件包裹 <App/>（或至少 <Suspense>/<Routes> 块），渲染可恢复的错误面板。
H-7 SQLite 单连接跨线程共享，设计正确但脆弱 HighConcurrency
backend/api/tasks.py:50, 59

单个 check_same_thread=False 连接被线程池 worker、看门狗线程与事件循环共享。当前所有访问都经 _db_lock 串行化（正确），但 _db_init() 在导入时未加锁（依赖单线程导入这一隐含前提）。整体可用但脆弱，无 SQL 注入（全部参数化）。

修复：考虑每线程连接池或 isolation_level=None，并显式记录"全部 DB 访问必须持锁"的约束。
H-8 WebSocket 队列泄漏 / 终态竞态：客户端可能永远收不到终态事件 HighConcurrency / 内存泄漏
backend/api/main.py:200-215 · tasks.py:209-214, 226-230

存在竞态窗口：ws_progress 在 get_task 返回非终态后、subscribe_ws 之前，任务可能完成并被 _update 弹出 _ws_queues[task_id]。订阅者随后注册的队列无人投喂、无人弹出，客户端将永远收不到终态，仅靠 30s 心跳维持直至断开。

修复：subscribe_ws 后重新检查任务状态（若已终态则补发终态并关闭）；终态时先向现存队列推送终态再让订阅者自行退订，而非直接 pop 整个队列列表。

🔵 低优先级问题 (Low)

backend/analyzer/functions.py:46-49

MD5 在 FIPS 模式系统上 hashlib.md5() 会抛 ValueError 致整个分析崩溃，并被 Bandit (B303/B324) 标记。

L-4 注解覆盖率对 __init__ 的返回槽不公平惩罚 Low正确性（轻微）
